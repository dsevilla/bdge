01 / IDENTIDAD

¿QUÉ ES CASSANDRA?

  • Sistema gestor de bases de datos NoSQL distribuido, de almacenamiento wide column, gratuito y de código abierto
  • Diseñado para manejar grandes cantidades de datos en muchos servidores que no tienen que ser de alto rendimiento, con alta disponibilidad y sin un punto único de fallo
  • Sólido soporte para clústeres que abarcan múltiples centros de datos, con replicación sin maestro asíncrona que permite operaciones de baja latencia para todos los clientes
02 / ORIGEN Y USO

¿DE DÓNDE VIENE?

  • Desarrollada por dos ingenieros de Facebook para el mecanismo de búsqueda del buzón de entrada
  • Facebook la lanzó como proyecto de código abierto en Google Code y después la entregó a la fundación Apache
  • Utilizada por organizaciones como Netflix, Apple, Weather Channel y eBay
03 / MODELO DE DATOS

DE SQL A CQL

  • En SQL, event_type referenciaba otra tabla; Cassandra no ofrece claves ajenas
  • Copiamos la descripción del tipo en cada evento, pero con id como clave sólo localizamos bien una fila por su identificador
CREATE TABLE events (
  id UUID PRIMARY KEY,
  time TIMESTAMP,
  event_type TEXT,
  data TEXT
);
04 / PRIMER REPARTO

UNA HORA, UNA PARTICIÓN

CREATE TABLE events (
  hour TIMESTAMP,
  id UUID,
  time TIMESTAMP,
  event_type TEXT,
  data TEXT,
  PRIMARY KEY (hour, id)
);
  • Los eventos de una hora se leen juntos
  • Si esa hora recibe muchas escrituras, concentra la carga en un nodo
05 / PARTICIÓN Y ORDEN

REPARTIR Y ORDENAR

CREATE TABLE events (
  hour TIMESTAMP,
  id UUID,
  time TIMESTAMP,
  event_type TEXT,
  data TEXT,
  PRIMARY KEY ((hour, event_type), time, id)
) WITH CLUSTERING ORDER BY (time DESC);
  • (hour, event_type) decide la partición; time, id ordenan las filas dentro de ella
06 / CUADRÍCULA DE UNA PARTICIÓN

LAS FILAS SE AGRUPAN

  • hour y event_type: clave de partición
  • time e id: orden dentro de la partición
  • data: valor del evento

Así leemos la tabla: cada fila repite 11:00 y click, los valores de su clave de partición

Es una vista lógica. En el siguiente paso, cómo queda la partición en disco

07 / EN DISCO

UNA PARTICIÓN, FILA TRAS FILA

  • La clave (11:00, click) se escribe una sola vez, al principio
  • Debajo, cada fila completa, en orden time DESC: sus valores de time e id la identifican
  • La celda data queda junto a su fila dentro de cada SSTable

Esquema simplificado: una partición puede aparecer en varias SSTables

No es columnar analítico (Vertica, Parquet): no hay un bloque por columna, cada fila guarda juntas sus celdas dentro de la SSTable

08 / DENTRO DEL CLÚSTER

SEIS NODOS, UN ANILLO

  • Cada nodo es responsable de un rango de tokens
  • Una petición puede entrar por cualquiera de ellos
  • Seguiremos una escritura de la partición (11:00, click)
09 / LLEGADA DE LA PETICIÓN

N4 ES EL COORDINADOR

  • El cliente envía a N4 una fila de events con su clave de partición
  • N4 coordina esta escritura; no es un nodo central fijo del clúster

El pequeño meteoro representa la petición del cliente

10 / CÁLCULO DEL DESTINO

EL HASH ELIGE EL RANGO

CLAVE(11:00, click)TOKEN ILUSTRATIVO87RANGO(79, 95] → N6

N4 aplica el partitioner a la clave completa; N6 es el primer nodo responsable de ese rango

El 87 procede del ejemplo del anillo en la sesión 5; no es el token real de esta clave

11 / ENVÍO A LAS RÉPLICAS

TRES COPIAS EN CAMINO

  • Con factor de replicación 3, se eligen N6 y los dos nodos siguientes del anillo: N1 y N2
  • N4 envía la misma partición directamente a los tres, en paralelo
12 / ESCRITURA DISTRIBUIDA

LA PARTICIÓN HA LLEGADO

PRIMER NODON6RÉPLICASN1 y N2COPIAS3 particiones completas

Cada nodo recibe las filas y sus campos juntos; las columnas no se reparten por separado

13 / INTERIOR DE N6

UNA ESCRITURA POR DENTRO

  • Commit log: registro de escrituras en disco
  • Memtable: datos recientes ordenados en memoria
  • SSTable: archivo inmutable en disco, creado más tarde

Seguimos una fila de events que N4 ha enviado a esta réplica

14 / PRIMER PASO

REGISTRAR LA ESCRITURA

  • N6 añade la operación al commit log en disco, en orden de llegada
  • El registro permite recuperar escrituras recientes tras un fallo
15 / SEGUNDO PASO

ACTUALIZAR LA MEMTABLE

  • La fila pasa a la memtable, que mantiene los datos en memoria ordenados por clave
  • Las barras ya presentes representan otras escrituras acumuladas
16 / CONFIRMACIÓN LOCAL

N6 RESPONDE A N4

  • Tras registrar y aplicar la escritura, N6 confirma al coordinador
  • La respuesta no espera a que la memtable se convierta en SSTable

N4 decide cuándo responder al cliente según el nivel de consistencia elegido

17 / MÁS TARDE

VOLCAR A DISCO

  • Al llenarse, la memtable se vuelca como una nueva SSTable
  • El bloque que viaja representa varias filas juntas, no un volcado por cada escritura
18 / RESULTADO

UNA SSTABLE INMUTABLE

  • Las filas volcadas quedan en un nuevo archivo ordenado en disco
  • La memtable anterior deja paso a otra; el segmento del commit log podrá reciclarse cuando todos sus datos estén volcados

La escena simplifica un proceso que ocurre con muchas escrituras y tablas
